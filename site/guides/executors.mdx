title: "Executors"

An executor is the coding agent that does the work inside the runner. Each task runs with one executor. You set executors up once as **executor profiles**, then pick one when you create a task.

## Agents you can use

When you add an executor profile, the **Agent** field offers two agents:

| Agent | Model format | Example |
| --- | --- | --- |
| **Claude Code** | A Claude model id or an alias such as `sonnet` or `opus` | `claude-sonnet-5-5` |
| **OpenCode** | Provider id and model id, separated by a slash | `anthropic/claude-sonnet-5-5` |

A custom executor is a profile you build on one of these agents: your own name, model and agent configuration (see [Advanced configuration](#advanced-configuration)). Self-hosted installs can also replace the runner image behind each agent.

## Personal and organization profiles

A profile lives in one of two scopes.

| | Personal | Organization |
| --- | --- | --- |
| Shown in Settings as | **My workspace** | **Organization** |
| Who can use it | You | Every member |
| Who can add or edit it | You | Organization admins |
| Limit | 10 profiles | 10 profiles |

In the task picker, personal profiles come first. Organization profiles are labelled `— organization`.

## Add a profile

<Steps>
  <Step title="Open Settings → Executors">
    The page is titled **Executors**.
  </Step>
  <Step title="Click Add executor">
    Use it under **My workspace**. Organization admins see an add button under **Organization** too.
  </Step>
  <Step title="Fill in the form">
    Give it a **Name**, such as `Code review`. The name appears in the task picker. Choose the **Agent**.
  </Step>
  <Step title="Connect a provider — optional">
    Open **Connect a provider** to give the profile its own key, endpoint and model: pick a provider
    (Anthropic, OpenRouter, OpenAI, LiteLLM — or, for OpenCode, **OpenAI-compatible** for your own
    endpoint such as vLLM, LiteLLM or a gateway), paste a key, set the base URL where the provider
    takes one, and name the model. The key is stored in the secret store — the configuration keeps
    only a reference to it. Bellows builds the agent configuration from what you pick; it stays
    visible and editable under **Advanced configuration**.
  </Step>
  <Step title="Or leave the provider out">
    Without a provider, keep **Use runner default** or choose **Custom model identifier** under
    **Model**. The task then runs on the key connected in [Settings → Model](/guides/onboarding), in
    your own or the organization's environment.
  </Step>
  <Step title="Save">
    Save the profile. It now shows in the task picker.
  </Step>
</Steps>

Names can't contain `/` or `\`, and can't start with `-` or `.`.

<Note>
Saving checks the form only. It doesn't test your credentials or whether the model exists. Anything
you leave unset is inherited from the runner's default configuration.
</Note>

### The key a provider profile carries

A key you paste through **Connect a provider** — or any key-shaped setting in the configuration — is
moved into the secret store. The configuration shows `stored-credential:` followed by a reference;
leave that text as it is to keep the key, or replace it with a new one. The task's agent receives
the real value when it starts.

For an **OpenAI-compatible** endpoint you can name a secret instead of pasting a key: choose
**Use a secret by name** and enter the variable's name — one set under **Settings → Environment** in
any scope (organization, workspace, or repository). Bellows writes the secret's value into the
configuration when a task starts, so **rotating the secret applies to the next task with no edit
here**. A name no scope holds fails the task before the agent starts, with a message naming the
missing variable. The deployment's own model credential is never a source for it: a reference
resolves only from your own scopes.

### Run an executor on a provider connection

A profile can select one **provider connection** — a named model key with its endpoint, set up under
**Settings → Model** — instead of relying on keys set in the environment. Several profiles can share
one connection, and each profile picks its own connection and model, so one connection's key
rotation reaches every profile that selects it on its next task, while a task already running keeps
the key it started with. Switching one profile to another connection changes nothing about the other
profiles or the connection itself.

- An organization profile can use organization connections only. A personal profile can use your own
  connections or the organization's. Promoting a personal profile to the organization is refused while
  it selects a personal connection.
- The connection's provider must be able to run the profile's agent: Anthropic, OpenRouter and LiteLLM
  run Claude Code and OpenCode, OpenAI runs OpenCode, and a Claude subscription runs Claude Code.
  A save, a task preflight and the task's start all refuse a pair that does not fit, and a connection
  that was deleted or is no longer yours is refused the same way — a task never falls back to a key from
  the environment.
- Switching a profile to another connection checks its model: a model that clearly belongs to another
  provider (for example `anthropic/…` on an OpenAI connection) is refused until you choose a model for
  the new connection. A model Bellows cannot place is kept; an unreachable model list never rejects one.
- A connection alone is a model credential: a profile that selects one needs no model key in the
  environment, in Bellows Cloud too.
- A connection's key and endpoint travel together. A connection on its provider's default endpoint
  never picks up a custom endpoint set elsewhere, and the keys, endpoints and routing settings it
  replaces are not passed to the task. Settings you paste into the profile's configuration are applied
  last and still win; that is deliberate, so a pasted endpoint or key overrides the connection.
- A connection that executors still select cannot be deleted. The refusal names the executors you can
  see and says only that others exist when you can't see them; remove or switch the executors first.

### Advanced configuration

Open **Advanced configuration** to edit the **Configuration JSON** directly. It must be a JSON object up to 32 KiB. A blank configuration is the same as `{}`. **Format JSON** tidies it.

The JSON is merged into the agent's own settings in the runner. Some keys are managed by Bellows and have no effect. The form lists any you set.

| Agent | Ignored keys |
| --- | --- |
| Claude Code | `hooks`, `enabledPlugins`, `extraKnownMarketplaces`, and the telemetry variables `CLAUDE_CODE_ENABLE_TELEMETRY` and `OTEL_*` under `env` |
| OpenCode | `permission` |

The same section has **gate repair rounds**: how many times the agent in a task on this executor gets a gate that failed at its finish back to fix, inside the same run. The default is 3, the maximum is 10, and `0` turns repair off. The value is fixed when the task is created. See [Gates](/guides/gates).

### Runner class

An organization profile can choose a **Runner class**: the kind of runner its tasks run on, such as one with more memory or one with Docker. The list holds the classes your deployment declares, and says for each whether it comes with Docker. **Deployment default** runs tasks on the deployment's usual runner. The **Organization** list shows the class beside the agent.

- Only organization profiles have a class. Personal profiles always run on the deployment default, and **Make personal** clears the class.
- Saving an edit saves the class shown in the form, so leaving it on **Deployment default** clears it.
- The class is read when a task starts, so a change applies to tasks that start afterwards.
- A class your deployment doesn't declare is refused when you save.

A class **with Docker** gives each task its own Docker daemon. Your gates get `DOCKER_HOST` pointing at it, so a gate command can run `docker` or `docker compose` when the `image` in your `.bellows.yaml` has the Docker CLI. The agent's own executor image has no Docker CLI, so the agent uses Docker through your gates, not directly. The daemon starts empty on every attempt. If it restarts while a gate fails, the attempt is interrupted and redone instead of counting as a failure. Docker classes exist only on Kubernetes.

<Warning>
A profile's own key is fine — the guided provider step stores it in the secret store, and the
configuration keeps only a reference. What the configuration must not carry is a key in plain text
you typed straight into the JSON: paste it through the guided fields instead, or set it as an
environment variable under **Settings → Workspace** (your own) or **Settings → Organization**
(shared).
</Warning>

A key that ends up in the configuration is never stored in it. Bellows moves the value of any
key-shaped setting, such as `ANTHROPIC_API_KEY` under `env` or an OpenCode provider's `apiKey`, into
the secret store. The configuration then shows `stored-credential:` followed by a reference. Leave
that text as it is to keep the key, or replace it with a new key. The task's agent still receives
the real value. Environment variables under **Settings → Workspace** (your own) or **Settings →
Organization** (shared) remain the other way to bring a key — the guided provider step links there.

<Note>
On Bellows Cloud, a configuration can't point the deployment's model credential at another host.
`ANTHROPIC_BASE_URL` or `OPENAI_BASE_URL` under `env`, or an OpenCode provider's `baseURL`, is
refused on save with `CREDENTIAL_REDIRECT_REFUSED` unless your own key is set with it:
`ANTHROPIC_API_KEY` or `OPENAI_API_KEY` under `env`, or the provider's own `apiKey` — pasted, or the
`{env:NAME}` reference to one of your own secrets. A task is checked again when it starts, against
the configuration together with every environment variable it receives, and fails before the agent
starts if the redirect has no key of yours. Self-hosted boards accept a redirect.
</Note>

<Note>
Bellows Cloud does not accept a Claude subscription OAuth token. A configuration that sets `CLAUDE_CODE_OAUTH_TOKEN` anywhere, for example under `env`, is refused on save with `CLOUD_CREDENTIAL_REFUSED`, and a profile saved with one earlier fails its task before the agent starts. Nothing saved is deleted. Use your own Anthropic API key (`ANTHROPIC_API_KEY`) instead. Self-hosted boards accept the token as before.
</Note>

## Pick an executor for a task

In the **New task** composer, the **Executor** chip next to **Repository** lists every profile you can use. Suspended profiles are not listed.

If you don't pick one, Bellows uses the first of these that exists:

1. Your default profile, while it is usable.
2. Your agent default: an agent and a model, with no profile. Set it under **Settings → Model**, or in the **Connect a model** setup step.
3. Your organization's agent default, which an admin sets.
4. Your first usable personal profile.
5. Your organization's first usable profile.

With none of these, Bellows refuses the task and links to **Add an executor in Settings**. A task on an agent default keeps that agent and model: changing the default later doesn't change a queued task, its retry or its follow-up.

### Choosing the model for one task

You can pick the model when you start a task, and again on a follow-up. It replaces the model of the profile or the agent default for that task only; the agent stays the same. Leave it empty to use the default. A follow-up without a model keeps the one the task last ran with, and so do a retry and a run that resumes after an interruption. Each run records the model it actually got.

In the composer, the **Model** chip sits next to the executor. It reads **Default**, or **Default (model)** when your agent default runs the task; leave it there to send no model. Open it to pick one of your provider's models, or type any model name and press Enter. The follow-up composer has the same chip, starting at the model the task is using; change it only to switch. The task page's **Execution** facts show the **Model** the latest run got, or **profile default** when the profile chose it.

From the CLI, pass `--model <name>` to `bellows job create` or `bellows job follow-up`. From an assistant, pass `model` to `create_task` or `follow_up_task`. A model name is 1 to 200 characters.

## Defaults and suspending

- **Make default** in a row's actions saves your own preference. The default row shows a **Default** tag, and the composer selects it for you. Each member chooses their own default, including among organization profiles.
- **Suspend** stops a profile from launching tasks. A suspended profile can't be a default. **Resume** brings it back.
- **Remove** deletes a personal profile. Admins can **Delete** an organization profile, or **Make personal** to move it into their own list.

Follow-ups and retries keep the executor of the original task.

## From the CLI

`bellows executor list` shows the profiles you can use. A profile with a runner class shows it as `class <name>`, and `--json` gives it as `runnerClass`, which is `null` for the deployment default.
