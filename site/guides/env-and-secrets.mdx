---
title: "Environment variables and secrets"
description: "Give the runner the values it needs, such as API keys and feature flags, at the organization, workspace or repository level."
---

Runners start with no knowledge of your private values. Add them in Settings and Bellows injects them into every run.

## Variable or secret

| | Variable | Secret |
| --- | --- | --- |
| Value shown after saving | Yes | No. It shows as `•••••••` |
| Use for | Flags, URLs, regions | API keys, tokens, passwords |
| Edit in `.env` text | Yes | No |

A secret is write-only. Once saved, nobody can read the value back, not even an admin. To change it, type a new value. To keep it, leave the field blank. The State column shows **Set**, **Not set** or **Will replace when saved**.

## Where to set them

Open **Settings**. Each scope has its own page:

| Scope | Settings page | Applies to |
| --- | --- | --- |
| Organization | **Organization** (section "Organization variables") | Every run in your organization |
| Workspace | **Workspace** (section "Workspace variables") | Only the runs you start |
| Repository | **Repositories**, then **Configure** on a repo | Only runs on that repository |

Organization and repository values reach every member's runs, so only an organization admin can save them. Every member saves their own workspace values.

<Steps>
  <Step title="Pick the tab">
    Choose **Variables** or **Secrets**. Each tab shows a count.
  </Step>
  <Step title="Add a row">
    Click **New variable** or **New secret**, then enter a name and a value.
  </Step>
  <Step title="Save">
    Click **Save changes**. Nothing is stored until you do. **Discard changes** drops your edits.
  </Step>
</Steps>

On the Variables tab, **Raw editor** lets you paste `.env` text instead. **List view** switches back.

<Note>
Saving sends the whole list for that scope. A name you remove from the list is deleted.

A save that sets or removes one name, such as the setup steps' model key, leaves every other name in the scope as it is. Two saves to the same scope at once are applied one after the other.
</Note>

## When a name is set in several places

The most specific scope wins:

```text
repository  >  workspace  >  organization
```

If `API_URL` is set in the organization and in a repository, runs on that repository get the repository value. Names that appear in only one scope are all kept.

## Limits and name rules

| Rule | Value |
| --- | --- |
| Entries per scope | 100 (variables and secrets together), counted on what the scope holds after the save |
| Name | Letters, digits and `_`, not starting with a digit. Up to 255 characters |
| Value | Up to 32,768 characters. No line breaks |

These names are reserved and are refused on save:

- `GITHUB_TOKEN` and `GH_TOKEN`. Bellows issues its own GitHub token for each run (see [Connections](/guides/connections)).
- Any name starting with `LD_`, plus `GCONV_PATH`, `GLIBC_TUNABLES`, `LOCPATH`, `NLSPATH` and `MALLOC_TRACE`.
- Names Bellows uses internally, such as `WORKDIR`, `BASE_BRANCH`, `RESTORE`, `REVIEW_REF`, and the `BELLOWS_*` and `SUPERVISOR_*` control names. The editor tells you when a name is refused.
- `OPENCODE_CONFIG_CONTENT` and `CLAUDE_CODE_CONFIG_CONTENT`.

On Bellows Cloud, `CLAUDE_CODE_OAUTH_TOKEN` is refused too, in every scope, with `CLOUD_CREDENTIAL_REFUSED`. A value saved earlier stays stored, but a task whose environment carries it fails before the agent starts. Use your own Anthropic API key (`ANTHROPIC_API_KEY`) instead. Self-hosted boards accept the token.

On Bellows Cloud, `ANTHROPIC_BASE_URL` and `OPENAI_BASE_URL` are refused with `CREDENTIAL_REDIRECT_REFUSED` unless the scope also holds your own key (`ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` for Anthropic, `OPENAI_API_KEY` for OpenAI) once the save is applied, saved earlier or in the same save. Without one, the runner would send the deployment's model credential to that host. When a task starts, Bellows checks every scope and the executor profile together, and the task fails before the agent starts if a redirect has no key of yours. A task whose environment sets `ANTHROPIC_BASE_URL` without your own `ANTHROPIC_API_KEY` runs with `ANTHROPIC_API_KEY` empty, and likewise `OPENAI_BASE_URL` without `OPENAI_API_KEY`, so the deployment's key is never sent to your host. Self-hosted boards leave the deployment's key in place beside a redirect.

### Claude Code with an OpenRouter key

Claude Code can run on an OpenRouter key alone. Save `OPENROUTER_API_KEY` in any scope and set no Anthropic key, token or base URL. When a Claude Code task starts, Bellows gives it `ANTHROPIC_BASE_URL=https://openrouter.ai/api`, your key as `ANTHROPIC_AUTH_TOKEN`, and an empty `ANTHROPIC_API_KEY`, so the deployment's own Anthropic key is never sent to OpenRouter. Name the model with its OpenRouter id, such as `anthropic/claude-sonnet-4`. Saving any of `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_BASE_URL` turns this off. A reviewer gets it only if its connections include `OPENROUTER_API_KEY`.

### Saving a model key from the model setup

The model setup (**Connect a model** during setup, and **Settings → Model** any time after) saves a provider key and your agent default in one step, in your workspace (**Only me**) or, for admins, for the organization (**Everyone in** your organization). Paste a key and the provider is picked from its prefix: `sk-ant-` Anthropic, `sk-or-` OpenRouter, `sk-proj-` OpenAI, `sk-ant-oat` a Claude subscription. Each provider stores its key under one name:

| Provider | Saved as | Agents |
| --- | --- | --- |
| Anthropic | `ANTHROPIC_API_KEY` | Claude Code, OpenCode |
| OpenRouter | `OPENROUTER_API_KEY` | OpenCode, Claude Code |
| OpenAI | `OPENAI_API_KEY` | OpenCode |
| LiteLLM | `ANTHROPIC_API_KEY` plus `ANTHROPIC_BASE_URL` (required) | Claude Code, OpenCode |
| Claude subscription | `CLAUDE_CODE_OAUTH_TOKEN` (self-hosted only) | Claude Code |

An optional base URL is saved as `ANTHROPIC_BASE_URL`, `OPENROUTER_BASE_URL` or `OPENAI_BASE_URL`. The setup shows the base URL (or LiteLLM proxy URL) already saved in the scope and saves it again unless you change it; one saved as a secret stays hidden and is kept, except a LiteLLM proxy URL, which you enter again so the key can be checked. Switching provider in a scope removes the previous provider's key and base URL from that scope only; other names stay. An OpenCode model is saved with its provider prefix, such as `openrouter/anthropic/claude-sonnet-4.5`. When the deployment supplies the model, you can pick an agent and model without a key. When your organization already has a key, the setup says so and you can start right away, or choose **Use a personal key**. A personal key wins over the organization's.

### Checking a key before you save

The model setup checks a key with its provider as you paste it, from the Bellows server. Nothing is saved until you click **Save**, which waits for the check to pass.

| Provider | A working key shows |
| --- | --- |
| Anthropic, OpenAI | How many models the key can use |
| OpenRouter | How many models, and the credit left on the account |
| LiteLLM | How many models the proxy serves for the key, and its budget when it has one |
| Claude subscription | That the token works |

A key that works but has no credit left shows a warning, and you can still save it. A refused key, or a provider Bellows can't reach, shows why, and **Save** stays unavailable. For LiteLLM the check reads the proxy's `/v1/models`, so a passing check does not prove your runners can reach the proxy too.

Each member can run 10 checks a minute. After that the check says to try again shortly. On Bellows Cloud, a Claude subscription token is refused before any check.

## Where the values are available

The values are set in the environment of the runner for each run. That includes your [`setup` command and gates](/guides/configure-repo) and the agent itself. They are not stored on the run's record.

<Warning>
The agent can read every variable and secret in its environment. Only add secrets you are happy for the agent, and any command it runs, to use. Prefer narrowly scoped keys, such as a test-environment key.
</Warning>

<Tip>
Put a value at the narrowest scope that needs it. A staging key used by one repo belongs on that repo, not on the organization.
</Tip>
