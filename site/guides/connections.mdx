## At a glance

| Service | What it is for | Who connects it |
| --- | --- | --- |
| GitHub | Cloning, branches, pull requests | Your organization, through the GitHub App |
| Jira | Tasks look up and comment on your Jira issues | You, with your own Atlassian account |
| Linear | Tasks look up and comment on your Linear issues | You, with your own Linear account |
| GitLab | Your organization's self-hosted GitLab; a member's own account | An admin connects the instance, each member links their account |
| Discord | Notifications about task events | You or an admin, through a webhook |

Open **Settings → Integrations** to see what you have connected. **Browse integrations** lists everything available.

## GitHub

GitHub is the base of Bellows. You sign in with GitHub, and your organizations are the places where the Bellows GitHub App is installed.

- **Sign in.** Click **Sign in with GitHub**. If you have no installation, you are asked to install the App first, then sign in again.
- **Your GitHub connection.** Signing in also connects your GitHub account to Bellows. **Settings → Integrations** shows **GitHub**, **Connected as** your login. If GitHub revokes it, the card says **Needs reconnect**; click **Reconnect GitHub**, which signs you in again. Signing in regularly keeps it current.
- **Pull requests are yours.** Bellows opens, edits and retargets a task's pull request as the member who started it, using this connection, so GitHub shows that member as the author. If the connection is broken at that moment, the task waits until the member reconnects, then continues. If the member cannot write to the repository, the task waits and retries about every 10 minutes until they get access or someone stops it.
- **Choose repositories.** On **Choose organizations and repositories**, pick what Bellows tracks. This changes what Bellows tracks, not your GitHub permissions.
- **What runs use it for.** For each run, Bellows issues a short-lived token limited to that one repository. The agent uses it to read and push code and work with issues; the pull request is opened by Bellows, not by the agent. There is no personal token to manage.

To add repositories later, ask an administrator to update the App installation on GitHub. Then open **Settings → Repositories**.

<Note>
You cannot set `GITHUB_TOKEN` yourself. See [Environment variables and secrets](/guides/env-and-secrets).
</Note>

## Jira

Connect Jira so that a task can read a ticket. Tasks can look issues up. If you allow it, they can also add comments. A connection belongs to you only. Admins cannot use it.

<Steps>
  <Step title="Open Integrations">
    Go to **Settings → Integrations**, then **Browse integrations**, and choose **Jira**.
  </Step>
  <Step title="Connect">
    Click **Connect**. In the **Connect Jira** dialog you can:
    - Fill **Jira site (optional)** with a site such as `acme.atlassian.net`. Leave it blank to allow every site your Atlassian account can reach.
    - Turn on **Allow adding comments**. Without it tasks can only look Jira up.
  </Step>
  <Step title="Approve in Atlassian">
    Click **Continue to Atlassian** and approve. You return to Bellows with a "Jira connected." notice.
  </Step>
</Steps>

You can also connect it during setup, right after your first sign-in. The **Connect your issue tracker** step shows GitHub as connected and a card for every issue tracker your deployment set up. Turn on **Allow adding comments** on a card if you want it, then click **Connect Jira**. You come back to the same step, which shows **Connected as** your account and site. **Skip for now** changes to **Continue**. If no tracker is set up, the step shows only GitHub. Connect one later in **Settings → Integrations**.

Each connection has its own page. There you can **Reconnect** or **Disconnect**. Reconnect with the same Atlassian account. If you turn on comments later, tasks already started with read-only access are refused until you start them again.

One Atlassian account can be connected in several Bellows organizations, and each organization holds its own connection. Inside one organization the account belongs to the member who connected it: another member who connects it sees "Jira connection failed (grant-conflict)." and nothing is connected.

### Using Jira on a task

Mention the ticket in the task, for example "Fix PROJ-123". When the task needs Jira and you have not connected it, the task page shows a block that says the task needs a Jira connection. Your options:

- **Connect Jira**, which opens the flow above.
- **Use selected connection**, if you have several. Pick the one this task uses.
- **Continue without it**.

The task stays queued, or pauses, until you choose. With Jira connected, the agent reads the ticket and sets the task title from the ticket's subject.

## Linear

Connect Linear so that a task can read an issue. Tasks can look issues up, search them and read their comments. If you allow it, they can also add comments. A connection belongs to you only. Admins cannot use it.

<Steps>
  <Step title="Open Integrations">
    Go to **Settings → Integrations**, then **Browse integrations**, and choose **Linear**.
  </Step>
  <Step title="Connect">
    Click **Connect**. In the **Connect Linear** dialog you can turn on **Allow adding comments**. Without it tasks can only look Linear up.
  </Step>
  <Step title="Approve in Linear">
    Click **Continue to Linear**, pick the workspace and approve. You return to Bellows with a "Linear connected." notice and a card for that workspace.
  </Step>
</Steps>

A connection reaches the one workspace you picked. Each connection has its own page, with **Reconnect** and **Disconnect**. Reconnect with the same Linear account and workspace. If you turn on comments later, tasks already started with read-only access are refused until you start them again.

### Using Linear on a task

Mention the issue in the task, for example "Fix PROJ-123", or paste its `linear.app` link. When the task needs Linear and you have not connected it, the task page shows a block that says the task needs a Linear connection, with the same choices as for Jira: **Connect Linear**, **Use selected connection** or **Continue without it**.

If a task is bound to both Jira and Linear, a bare key such as `PROJ-123` could belong to either, so the agent asks you which one before it reads or comments. With Linear connected, the agent reads the issue and sets the task title from its subject. Creating, assigning or moving Linear issues is not supported.

## GitLab

<Note>
GitLab support is being built in steps. Bellows starts tasks on GitLab repositories, but cannot yet read their branches or skills, or open merge requests.
</Note>

An organization can connect a self-hosted GitLab instance, and each member then links their own GitLab account. Bellows acts as that member, never through a shared token.

Everything below is on **Settings → Integrations → GitLab** (the **GitLab** link on the Integrations page). An admin fills in the host, the OAuth application ID and secret, the allowed root groups and, for a private CA, the CA bundle, then presses **Connect GitLab**. The connection shows **Pending** until **Activate** has sent the admin to GitLab to authorize and the instance has answered as GitLab 17.0 or later; if it is older the page says so and the connection stays pending, and if GitLab cannot be reached it says that too and nothing is refused or deleted. An active connection offers **Load projects**: tick the projects to track and press **Save tracked projects**. A list GitLab could not give is shown as an error with **Retry**, never as an empty list, and a tracked project missing from your list stays shown, marked as no longer listed. A path already tracked under another forge is refused with the reason. **Remove** ends the connection and everyone's links to it. Every member sees **Your account** for each active instance, with **Link GitLab account**, or **Reconnect GitLab account** when the link needs renewing, and **Linked** when it is live. A linked member can press **Link a different account** to replace the link with another GitLab account (sign in to that account on GitLab first); there is no unlink, and removing the instance ends everyone's links.

The calls below do the same from a script. They need a signed-in session or a personal access token, and the connect, activate and choose-repositories calls are admin-only.

1. **Register an OAuth application on GitLab** with scope `api` and the redirect URI `<your Bellows URL>/api/forge-grants/gitlab/callback`.
2. **Connect the instance** (admin): `POST /api/org/gitlab-connections` with `host` (a bare host, optional port), `clientId`, `clientSecret`, `allowedGroups` (root group paths) and, for a private CA, `caBundle` (PEM). The secret and the bundle are stored encrypted and never shown again. The connection starts **pending**; Bellows only checks that the instance answers.
3. **Activate it** (admin): `POST /api/org/gitlab-connections/{id}/activation` returns an `authorizeUrl`. Open it in your browser while signed in to Bellows and authorize on GitLab. Bellows then asks GitLab for its version with your authorization, and activates the connection only if it is **GitLab 17.0 or later**. On an older version the connection stays pending and `activationRefusal` says `version-too-old`. If GitLab cannot be reached or answers something unexpected, nothing changes and nothing is deleted: try again.
4. **Link your account** (every member, once the connection is active): `POST /api/forge-grants/gitlab/{id}/link` returns an `authorizeUrl` to open the same way, and `GET /api/forge-grants/gitlab` lists the active connections and whether you are `live`, `broken` or `missing` on each. Bellows asks for scope `api` only.

5. **Choose the repositories** (admin, once you have linked your own account): `GET /api/org/gitlab-connections/{id}/projects` lists the projects you can see under the allowed root groups, subgroups included, each with a `tracked` flag. A project that is tracked but not in your list (another admin's, archived or deleted) is still shown, with `listed: false`. `PUT /api/org/gitlab-connections/{id}/tracked-repos` with `{"paths": ["group/project", …]}` replaces the organization's tracked projects on that host with exactly those paths, and an empty list tracks none. For now a project path can be tracked only once per organization, across GitHub and every GitLab host: saving a path that is already tracked elsewhere is refused with `TRACKED_PATH_CONFLICT` naming it, and nothing is changed. If the connection is removed or replaced while you are choosing, the save is refused with `GITLAB_CONNECTION_CHANGED` and nothing is written: reload and choose again. Only projects in that listing, or already tracked, are accepted, and a tracked project is dropped only when you leave it out. It never touches your GitHub repositories, and removing the connection untracks its projects. If GitLab does not answer cleanly the list is not shown partly and nothing is saved: try again.

After either authorization Bellows sends you back to **Settings → Integrations** with `integration=gitlab` and a `result` in the address: `activated` or `linked`, or the reason it did not finish (for example `denied`, `version-too-old` or `unconfirmed`). Each authorization link works once and only for the person who started it.

### Starting work on a GitLab repository

A task, follow-up, retry, reopen or batch on a tracked GitLab project needs your own live GitLab link, and GitLab must say you hold **Developer access or higher** on the project (your own role or one inherited from a group). Without a link the start is refused with `FORGE_GRANT_REQUIRED` and a link to **Settings → Integrations → GitLab**. With a link but less than Developer access it is refused with `FORGE_ACCESS_DENIED`, naming the project: ask for access on GitLab, or link a different account. The page shows the same refusal in words, with an **Open GitLab settings** link. If GitLab does not answer the access check, the start fails with a retryable `503` and nothing is queued; start again. Preflight shows both as the `forge` check.

A task that is already running when your GitLab link is revoked or needs reconnecting is not failed. Bellows finds out when the task next asks for your credential, stops the agent, and holds the task, keeping its session and checkout. The task page shows it as paused, with a **Reconnect** link to the GitLab settings. It starts again by itself once you link again.

### When you need to reconnect

A link is `broken` and you must link again (run the link step once more) when:

- GitLab no longer accepts the grant: you revoked the application on GitLab, or it was rotated away.
- A token refresh got no clear answer. GitLab replaces a refresh token each time it is used, so after a lost, timed-out or gateway-error answer Bellows cannot tell whether the old token is already spent. It never tries it again; it asks you to reconnect instead.

Nothing is deleted when this happens, and linking again makes the grant live. Removing a GitLab connection revokes everyone's links to it, so they link again once the host is connected anew. Two organizations connecting the same GitLab host keep separate applications and separate links.

## Discord notifications

Discord sends task events to a channel you choose. It uses a webhook, not an account login.

<Steps>
  <Step title="Create a webhook in Discord">
    In your Discord channel settings, create a webhook and copy its URL. Only `discord.com` and `discordapp.com` webhook URLs (`/api/webhooks/…`) are accepted.
  </Step>
  <Step title="Add the notification in Bellows">
    - **Settings → Workspace**, section **My notifications**, for updates to your own tasks.
    - **Settings → Organization**, section **Organization notifications**, for a channel shared by the whole organization. Admins can write it.

    Click **Add notification**, choose the **Channel** (Discord), paste the **Webhook URL** and pick the **Events**.
  </Step>
  <Step title="Test it">
    Use **Send test notification** on the row to check it works.
  </Step>
</Steps>

Events you can pick: **Task ready**, **Task blocked**, **Task has a question** and **Admin action on a task**. You can limit a notification to some repositories (one per line, empty for all) and switch it off with the **Enabled** toggle.

The webhook URL is stored encrypted and never shown again. When you edit a notification, leave the field blank to keep it.
