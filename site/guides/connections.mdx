## At a glance

| Service | What it is for | Who connects it |
| --- | --- | --- |
| GitHub | Cloning, branches, pull requests | Your organization, through the GitHub App |
| Jira | Tasks look up and comment on your Jira issues | You, with your own Atlassian account |
| Linear | Tasks look up and comment on your Linear issues | You, with your own Linear account |
| Discord | Notifications about task events | You or an admin, through a webhook |
| Model providers | The key and endpoint an executor's model runs on | You (your own) or an admin (the organization's), under **Settings → Model** |

Open **Settings → Integrations** to see what you have connected. **Browse integrations** lists everything available.

## Model provider connections

A provider connection is a named model key with its endpoint — Anthropic, OpenRouter, OpenAI, LiteLLM, or on self-hosted boards a Claude subscription. Executors select one by name, so several can share a key and a rotation reaches them all. They are separate from the Jira, Linear and Discord connections above.

Manage them under **Settings → Model → Provider connections**:

- **Add connection.** Pick who can use it (**Only me**, or **Everyone in the organization** for admins), a name, the provider, the key and, where one fits, an endpoint. Bellows checks the key and shows how many models it offers; **Save** waits for a working key.
- **Edit.** Rename it or change its endpoint. This never touches the stored key.
- **Replace key.** Check and save a new key. A task already running keeps the key it started with.
- **Show models.** Reads the connection's live models. An empty list, a provider that does not list models, and a failed read are shown differently.
- **Remove.** Refused while an executor still selects it; the message names the executors you can see.

**Connect a model** (setup, or **Settings → Model**) creates a connection and the executor that runs on it together. Creating a connection, choosing an existing one and replacing a key are different actions: choosing one or changing only the model leaves its key as it is, and **Replace the key** changes that connection in place. A name already used by another connection in the same scope is refused instead of overwriting it, so two connections for one provider never replace each other by accident.

Organization connections are managed by admins and usable by every member's executors; personal connections are yours alone. A key is never shown again after it is saved. See [Executors](/guides/executors) for choosing a connection.

## GitHub

GitHub is the base of Bellows. You sign in with GitHub, and your organizations are the places where the Bellows GitHub App is installed.

- **Sign in.** Click **Sign in with GitHub**. If you have no installation, you are asked to install the App first, then sign in again.
- **Choose repositories.** On **Choose organizations and repositories**, pick what Bellows tracks. This changes what Bellows tracks, not your GitHub permissions.
- **Add another organization.** Only organizations with the App installed are listed, so a new organization does not appear until you install the App on it. Click **Install the App on another organization**, on the selection screen or under **Account → Tracked organizations**. After installing, you return to the selection screen with the new organization selected.
- **What runs use it for.** For each run, Bellows issues a short-lived token limited to that one repository. The agent uses it to read and push code, open the pull request and work with issues. There is no personal token to manage.

To add repositories later, ask an administrator to update the App installation on GitHub. Then open **Settings → Repositories**.

<Note>
You cannot set `GITHUB_TOKEN` yourself. See [Environment variables and secrets](/guides/env-and-secrets).
</Note>

## Jira

Connect Jira so that a task can read a ticket. Tasks can look issues up. If you allow it, they can also add comments. A connection belongs to you only. Admins cannot use it.

<Steps>
  <Step title="Open Integrations">
    Go to **Settings → Integrations**, then **Browse integrations**, and choose **Jira**.
  </Step>
  <Step title="Connect">
    Click **Connect**. In the **Connect Jira** dialog you can:
    - Fill **Jira site (optional)** with a site such as `acme.atlassian.net`. Leave it blank to allow every site your Atlassian account can reach.
    - Turn on **Allow adding comments**. Without it tasks can only look Jira up.
  </Step>
  <Step title="Approve in Atlassian">
    Click **Continue to Atlassian** and approve. You return to Bellows with a "Jira connected." notice.
  </Step>
</Steps>

You can also connect it during setup, right after your first sign-in. The **Connect your issue tracker** step shows GitHub as connected and a card for every issue tracker your deployment set up. Turn on **Allow adding comments** on a card if you want it, then click **Connect Jira**. You come back to the same step, which shows **Connected as** the site, since a Jira connection keeps no email or name. **Skip for now** changes to **Continue**. If no tracker is set up, the step shows only GitHub. Connect one later in **Settings → Integrations**.

Each connection has its own page. There you can **Reconnect** or **Disconnect**. Reconnect with the same Atlassian account. If you turn on comments later, tasks already started with read-only access are refused until you start them again.

Bellows stores your Atlassian account id and the site, not your email or display name. The site host is shown as the account.

A Jira connection ends on its own when you can no longer use it: you leave the Bellows organization, you lose access to the site in Atlassian, or Atlassian refuses to renew the grant. Bellows checks about once an hour. The connection disappears from **Settings → Integrations**, its stored token is destroyed, and the audit log records a `connection.revoke` row. Connect again to use Jira. Until Bellows notices, a task that uses the connection fails at Atlassian.

One Atlassian account can be connected in several Bellows organizations, and each organization holds its own connection. Inside one organization the account belongs to the member who connected it: another member who connects it sees "Jira connection failed (grant-conflict)." and nothing is connected.

### Using Jira on a task

Mention the ticket in the task, for example "Fix PROJ-123". When the task needs Jira and you have not connected it, the task page shows a block that says the task needs a Jira connection. Your options:

- **Connect Jira**, which opens the flow above.
- **Use selected connection**, if you have several. Pick the one this task uses.
- **Continue without it**.

The task stays queued, or pauses, until you choose. With Jira connected, the agent reads the ticket and sets the task title from the ticket's subject.

## Linear

Connect Linear so that a task can read an issue. Tasks can look issues up, search them and read their comments. If you allow it, they can also add comments. A connection belongs to you only. Admins cannot use it.

<Steps>
  <Step title="Open Integrations">
    Go to **Settings → Integrations**, then **Browse integrations**, and choose **Linear**.
  </Step>
  <Step title="Connect">
    Click **Connect**. In the **Connect Linear** dialog you can turn on **Allow adding comments**. Without it tasks can only look Linear up.
  </Step>
  <Step title="Approve in Linear">
    Click **Continue to Linear**, pick the workspace and approve. You return to Bellows with a "Linear connected." notice and a card for that workspace.
  </Step>
</Steps>

A connection reaches the one workspace you picked. Each connection has its own page, with **Reconnect** and **Disconnect**. Reconnect with the same Linear account and workspace. If you turn on comments later, tasks already started with read-only access are refused until you start them again.

### Using Linear on a task

Mention the issue in the task, for example "Fix PROJ-123", or paste its `linear.app` link. When the task needs Linear and you have not connected it, the task page shows a block that says the task needs a Linear connection, with the same choices as for Jira: **Connect Linear**, **Use selected connection** or **Continue without it**.

If a task is bound to both Jira and Linear, a bare key such as `PROJ-123` could belong to either, so the agent asks you which one before it reads or comments. With Linear connected, the agent reads the issue and sets the task title from its subject. Creating, assigning or moving Linear issues is not supported.

## Discord notifications

Discord sends task events to a channel you choose. It uses a webhook, not an account login.

<Steps>
  <Step title="Create a webhook in Discord">
    In your Discord channel settings, create a webhook and copy its URL. Only `discord.com` and `discordapp.com` webhook URLs (`/api/webhooks/…`) are accepted.
  </Step>
  <Step title="Add the notification in Bellows">
    - **Settings → Workspace**, section **My notifications**, for updates to your own tasks.
    - **Settings → Organization**, section **Organization notifications**, for a channel shared by the whole organization. Admins can write it.

    Click **Add notification**, choose the **Channel** (Discord), paste the **Webhook URL** and pick the **Events**.
  </Step>
  <Step title="Test it">
    Use **Send test notification** on the row to check it works.
  </Step>
</Steps>

Events you can pick: **Task ready**, **Task blocked**, **Task has a question** and **Admin action on a task**. You can limit a notification to some repositories (one per line, empty for all) and switch it off with the **Enabled** toggle.

The webhook URL is stored encrypted and never shown again. When you edit a notification, leave the field blank to keep it.
