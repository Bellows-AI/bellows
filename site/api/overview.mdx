Use the REST API when you want to start or follow tasks from a script, a CI job or your own integration. The [CLI](/cli/install) and the MCP server call the same task routes, so anything they do you can do over HTTP.

<Note>
Bellows has no published OpenAPI spec. This page lists the routes you are most likely to script against. For everything else, the [CLI](/cli/commands) covers the same actions with ready-made flags.
</Note>

## Base URL

All routes live under `/api`. On Bellows Cloud that is `https://bellows.cloud/api`; self-hosted, use your server's URL. Bodies and answers are JSON unless a route says otherwise.

## Authenticate

Send an access token in the `Authorization` header:

```http
Authorization: Bearer fat_...
```

| Token | Prefix | Acts as | What it can do |
| --- | --- | --- | --- |
| Personal access token | `fat_` | You | Everything you can do in the app, including creating tasks. Tasks it creates show you as the author. |
| Organization access token | `oat_` | The organization | Read only. Writes answer `403`. |

Use a `fat_` token for scripts that create or steer tasks. Use an `oat_` token for automation that only reads and should outlive any one member.

### Create a token

<Steps>
  <Step title="Open Account">
    Open the user menu and choose **Account**.
  </Step>
  <Step title="Create the token">
    Under **Personal access tokens**, enter a label in **Token label** ("what this token is for") and press **Create token**. For an organization token, use **Organization access tokens**. Only admins see that section.
  </Step>
  <Step title="Copy it now">
    Bellows shows the token once. Copy it, then press **Done**. Only a hash is stored, so a lost token cannot be shown again. Create a new one.
  </Step>
</Steps>

The list shows **Label**, **Created** and **Last used** for each token. To revoke one, use **Revoke** on its row and confirm.

<Warning>
Treat a token like a password. Keep it in your CI secret store, never in a repository or a command line. The create form has no expiry or scope setting. Revoke a token when you stop using it.
</Warning>

<Note>
The MCP server uses its own sign-in (OAuth), not these tokens. A `fat_` or `oat_` token is not accepted there, and MCP tokens are not accepted on the other routes.
</Note>

## Core routes

`:id` is a job id. Creating a task returns the id of its first job, and that id also identifies the task.

| Method and path | What it does |
| --- | --- |
| `POST /api/jobs` | Create a task. Body: `command` (the prompt), plus optional `repo` (`owner/name`), `executor`, `executorScope` (`user` or `org`), `baseBranch`, `title`, `skills`, `connections`, `attachments`. Answers `201 {id, status}`. |
| `GET /api/jobs/:id` | Read one job. Add `?waitFor=terminal&timeout=<seconds>` to hold until the run settles. |
| `GET /api/jobs` | List jobs, newest first. Query: `status`, `repo`, `limit`. |
| `GET /api/tasks` | List tasks the way the inbox does. Answers `{page}`. |
| `POST /api/jobs/:id/follow-up` | Queue new instructions on the same task. Body: `command`, optional `attachments`. |
| `POST /api/jobs/:id/questions/:questionId/answer` | Answer a question from the agent. Body: `{answers}`, a map from each question prompt to your answer. |
| `POST /api/jobs/:id/stop` | Stop a run. No body. |
| `POST /api/jobs/:id/retry` | Retry a failed run. No body. Answers `201`. |
| `POST /api/jobs/:id/done` | Mark the task done. Send `{"force": true}` to force it. |
| `POST /api/jobs/:id/reopen` | Reopen a done task. |
| `GET /api/repos` | Repositories you can run tasks on. |
| `GET /api/workspace` | Your executors (`executors`), the organization's (`orgExecutors`) and the default (`defaultExecutor`). |
| `POST /api/attachments` | Upload one file. See below. |
| `GET /api/attachments/limits` | The accepted file formats and sizes. |
| `POST /api/jobs/preflight` | Check a repo, executor and skills selection without creating a task. |

`GET /api/jobs` takes `status` as one of `queued`, `running`, `succeeded`, `failed`, `dead`, `stopped`, or `terminal` for every finished status. `limit` is 1 to 200 and defaults to 50. What each state means: [Task lifecycle](/guides/task-lifecycle).

### Upload an attachment

Send the raw file as the body with `Content-Type: application/octet-stream` and the file name, percent-encoded, in `X-Attachment-Name`. Add an `Idempotency-Key`. The answer is `{id}`. Pass that id in the `attachments` list of a create or a follow-up. Each file can be up to 20 MiB. Formats and the other limits: [Attachments](/guides/attachments).

### Idempotency keys

`POST /api/jobs`, follow-up and retry accept an `Idempotency-Key` header: 8 to 128 letters, digits or `. _ : -`. Repeat the request with the same key after a lost answer and you get the task the first attempt made. The answer carries `Idempotency-Replayed: true`. The same key with a different body is refused.

## Errors

A refused request answers with an HTTP status and a JSON body with a human message and a stable code:

```json
{ "error": "label must be 1 to 128 characters", "code": "BAD_LABEL" }
```

Branch on `code`, not on the message.

| Status | Meaning |
| --- | --- |
| `400` | A field is invalid. The code names it, for example `BAD_COMMAND`, `BAD_REPO`, `BAD_STATUS`, `BAD_LIMIT`. |
| `401` | No token, or an unknown or revoked one. Code `UNAUTHENTICATED`. |
| `403` | The token authenticated but may not do this. An `oat_` token on a write gets `FORBIDDEN`. |
| `404` | No such job or token. Code `NOT_FOUND`. |
| `409`, `422` | The request was understood but conflicts with the current state, or names something that does not exist, for example an unknown executor or base branch, or a reused idempotency key. |

## Limits

- A create or follow-up body can be up to 128 KiB. An answer body can be up to 64 KiB. Most other write routes take 4 KiB.
- `GET /api/jobs/:id?waitFor=terminal` holds for 30 seconds by default. `timeout` can be 1 to 60 seconds, and a larger value is capped at 60.
- Uploads: up to 10 files per request, 20 MiB each.

Bellows documents no request-rate limit for these routes. Poll with a pause, or use the wait parameter instead of a tight loop.

## Example: create a task and print the PR

This script creates a task, waits for the run to settle, and prints the pull request URL.

```bash run-task.sh
#!/usr/bin/env bash
set -euo pipefail

: "${BELLOWS_TOKEN:?set a personal access token (fat_...)}"
API="https://bellows.cloud/api"
AUTH="Authorization: Bearer $BELLOWS_TOKEN"

# 1. Create the task.
ID=$(curl -fsS -X POST "$API/jobs" \
  -H "$AUTH" -H "Content-Type: application/json" \
  -H "Idempotency-Key: ci-$(date +%s)-$$" \
  -d '{"repo":"acme/notes-api","command":"Add a /health endpoint that returns 200 and the app version."}' \
  | jq -r .id)
echo "task $ID"

# 2. Wait. Each call holds up to 60 seconds, so this loop is not a busy poll.
while true; do
  RESULT=$(curl -fsS -H "$AUTH" "$API/jobs/$ID?waitFor=terminal&timeout=60")
  case "$(echo "$RESULT" | jq -r .result)" in
    terminal) break ;;
    parked) echo "task is waiting on a workflow step" >&2; exit 6 ;;
  esac
done

# 3. Read the outcome.
STATUS=$(echo "$RESULT" | jq -r .headStatus)
if [ "$STATUS" != "succeeded" ]; then
  echo "run ended as $STATUS" >&2
  echo "$RESULT" | jq -r '.job.summary // empty' >&2
  exit 1
fi
echo "$RESULT" | jq -r '.job.publication.prUrl // "no PR recorded"'
```

The wait answer holds `result` (`terminal`, `parked` or `timeout`), `headStatus` (the newest run's status) and `job` (the run you asked for). The pull request is in `job.publication.prUrl`.

<Tip>
If the agent asks a question, it appears in `job.questions`. Answer with `POST /api/jobs/:id/questions/:questionId/answer`, or use [`bellows job answer`](/cli/commands).
</Tip>
