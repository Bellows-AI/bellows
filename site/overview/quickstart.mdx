## Before you start

- A GitHub repository you can install apps on
- Commands that build and test it (we'll use `make build` and `make test`)

The examples use a small Go web server with lorem ipsum and notes endpoints. Any language works.

## Steps

<Steps>
  <Step title="Add .bellows.yaml to the repo root">
    This file sets the runner's container and the checks every run must pass. Add it first, so your first task already runs them.

    ```yaml .bellows.yaml
    environment:
        image: golang:1.25
        setup: "go mod download"
        gates:
            - name: build
              command: "make build"
              timeout: 5
            - name: test
              command: "make test"
              timeout: 10
    ```

    Commit and push it to the default branch.
  </Step>
  <Step title="Sign in and choose repositories">
    Sign in with GitHub, install the Bellows GitHub App, then choose the organizations and repositories Bellows should track. This is step 1 of 3.

    <Frame>
      <img src="/images/quickstart/01-onboarding.png" alt="Onboarding: choose organizations and repositories" />
    </Frame>
  </Step>
  <Step title="Connect a provider">
    Step 2 has two parts. In **Provider connection**, choose Anthropic, OpenRouter, OpenAI, LiteLLM or an OpenAI-compatible custom endpoint (self-hosted boards, and cloud organizations the operator enabled, also offer a Claude subscription), and paste a key. Bellows picks the provider from the key's prefix and checks the key with the provider. Choose who uses the connection (**Everyone in** the organization, admins only, or **Only me**) and give it a name, or keep the suggestion; a name that is already in use is refused, never overwritten. In **Default executor**, which stays dimmed until the key checks out, choose the agent (fixed when the provider runs only one) and the default model: pick one the provider lists or type any model name it serves. The executor's name follows the agent and model, such as *Claude Code · Sonnet*, until you edit it. **Create and continue** seals the key in a provider connection, creates the executor on it and makes it your default (or the organization's). Change either later under **Settings → Model** and **Settings → Executors**. If your organization already has a default executor, the step names it and the connection it runs on, and **Continue** moves on; **Add another provider** and **Replace the key** are there too. See [Saving a model key](/guides/env-and-secrets#saving-a-model-key-when-you-connect-a-provider).

    <Frame>
      <img src="/images/quickstart/07-connect-model.png" alt="Setup step 2: connect a provider" />
    </Frame>
  </Step>
  <Step title="Connect your issue tracker">
    Step 3 is optional: connect your issue tracker, such as Jira or Linear, so tasks can read the ticket they link to. Each step has **Skip for now**, and **Back** returns to the step before. Until you finish, opening Bellows brings you back to the step you stopped at.

    <Frame>
      <img src="/images/quickstart/08-connect-tracker.png" alt="Setup step 3: connect your issue tracker" />
    </Frame>
  </Step>
  <Step title="Start your first task">
    The last page, **You're set**, lists what you set up — GitHub, your repositories, the provider, the default executor and the issue tracker — each with **Change** to go back to its step. Below it is the task composer, with your first repository already chosen. Describe the change, or click a starter (**Write CONTRIBUTING.md**, **Fix a flaky test**, **Upgrade a dependency**), then press `Enter` (`Shift + Enter` adds a new line; on a phone, tap the round arrow, **Start task**). The task runs on your default executor, the one the provider step created, and Bellows opens its page.

    ```text Task
    Add a GET /api/notes/count endpoint that returns {"count": N}.
    Add a table test in internal/server/server_test.go.
    ```

    <Frame>
      <img src="/images/quickstart/03-new-task.png" alt="The You're set page with the task composer" />
    </Frame>

    **Go to the dashboard instead** finishes setup without starting a task; later tasks start from **New task**. If you skipped the provider, the summary says so, and a task you start is refused until you have an executor: connect a provider under **Settings → Model** and choose a default executor.
  </Step>
  <Step title="Answer questions, if any">
    Some tasks need a decision from you. The agent asks inline and waits. Pick an answer and click **Submit**.

    <Frame>
      <img src="/images/quickstart/04-question.png" alt="Agent question waiting for an answer" />
    </Frame>
  </Step>
  <Step title="Review and finish">
    Once the gates pass, Bellows opens a pull request and the task shows <span className="status status-review">Waiting for review</span>. Review the PR on GitHub. If it needs changes, use **Follow up** on the task. Once it's merged, click **Mark done**.

    <Frame caption="The task page: conversation and follow-up on the left; outcome, verification and the published PR on the right.">
      <img src="/images/quickstart/05-task-review.png" alt="Task waiting for review with a published pull request" />
    </Frame>
  </Step>
</Steps>

## What just happened

<div className="status-flow">
  <span className="status status-queued">Queued</span> → <span className="status status-running">Running</span> → <span className="status status-running">Gates: build, test</span> → <span className="status status-review">Waiting for review</span> → <span className="status status-done">Done</span>
</div>

The driver started a `golang:1.25` runner and ran `setup`. Then the agent made the change. Bellows ran each gate, and the PR opened only after all of them passed.

<Tip>
  Writing a good task description is the biggest lever on results. See [Writing good tasks](/guides/writing-good-tasks).
</Tip>
