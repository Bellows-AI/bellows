## Invariants

- A workspace skill is owned by one member and an org skill by the organization; another owner's id is `404 SKILL_NOT_FOUND`, never `403`.
- A version is immutable; equal content reuses its row. Delete is soft and a version stays readable for a pin until the sweep.
- A name starting `factory-` is refused (`422 SKILL_BUNDLE_INVALID`, reason `reserved_name`); a taken name in the same scope is `409 NAME_TAKEN`; a workspace and an org skill may share a name, the workspace one wins.
- A switched-off built-in is out of the org's catalog, not out of the board: it is `not installed` to a selection and `unverified` (never absent, never known) while the switched-off list cannot be read.
- A stored skill's `metadata:` `requires-tools` / `requires-connections` are parsed at upload (`parseSkillRequirements`), refused `422 SKILL_BUNDLE_INVALID` with reason `unknown_tool` / `unknown_connection`, and stored on its version; an identical re-upload sets them on the existing version. Stated limit: a version uploaded before requirements were stored declares none until re-uploaded.
- Promote is workspace to org, admin only, and `409` when the org already has the name.
- An inline edit whose current version cannot be read writes nothing: `410 SKILL_GONE` or `503`, never a version holding SKILL.md alone. `server/test/routes.skills-store.test.ts`.
- An unconfirmed read is never "no skills": a lost object is `410 SKILL_GONE`, an unreachable store or object is `503`.
- The object key is per org (`<prefix>_skills/<org>/<sha256>`); only the sweep deletes objects. Stated limit: an upload whose transaction then fails or loses a name race leaves an unreferenced object that nothing lists or sweeps.
- The catalog limits and per-layer precedence for selection stay in [docs/jobs.md](jobs.md).
- A pin is never re-resolved across claims: a takeover or user retry delivers the versions the row was made with, even for a skill disabled or deleted since; only a follow-up resolves again. A pinned version a runner cannot fetch is `410`/`422`, never `404`, so it cannot read as "not pinned".
- Delivery outcomes: `skill_unavailable` (a gone, corrupt, tampered or unsafe bundle) fails the task and rests a workflow thread; every other failure, an unreadable pin included, throws and the lease hands the claim back. Skills are never mounted under `/etc/claude-code`.
- A pinned org skill whose name the checkout also holds where the task's CLI scans (claude-code: `.claude/skills`; opencode: that, `.opencode/skills`, `.opencode/skill`, `.agents/skills` — `checkoutSkillDirsOf` in `driver/src/skill-inputs.ts`) is not installed: the repo's copy is the only one, on both executors (`driver/src/scripts/skill-install.cjs`, `driver/test/scripts-skill-install.test.ts`, `driver/test/skill-inputs.test.ts`, lane `pinned-skills`). Stated limits on a pinned workspace skill the checkout also holds: on claude-code it ranks below the repo's (`--add-dir`; a link into the config dir would win but is cited under the 0700 config dir, which the tool uid cannot read), on opencode exactly one copy is listed but which source wins (`skills.paths` or repo) is a race that load decides (BEL-286 S5 measurement), so `docker/opencode-executor/test.sh` asserts one copy from an expected source, never the winner.
- A row's hidden skills are never re-read by a claim, takeover or retry; a connection bound after the row was made un-hides nothing until a follow-up decides again, and a failed read inside the deciding transaction fails the create or follow-up whole.
- Hiding is a listing rule, not an access control: a reviewer container's CLI and tools share one uid, so its agent could rewrite its own `/tmp/.factory-skills`, and every helper stays readable by path. Nothing may be mounted over `/tmp/.factory-skills` (`driver/test/k8s/pod-spec.test.ts`).
