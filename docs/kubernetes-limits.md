# Kubernetes limits

The stated limits, takeover behaviour and EKS prerequisites of the kubernetes executor; the map to the code is [kubernetes.md](kubernetes.md).

## Stated limits

- Stated limit: a runner still RUNNING when its driver is lost, its agent released by the supervisor, is taken over: the next claim rebinds the supervisor (`rebind`), the supervisor must poll the new endpoint within `SUPERVISOR_REBIND_DELIVERY_MS`, and no sync, setup or `go` follows; one never released is swept by the next claim's re-claim fence and the job redone in its session and tree, an interruption inside the budget; one whose agent exited is taken over the same way while its supervisor still serves (no `supervisor: stopped serving the steps`), its report delivered to the new holder; one whose supervisor stopped serving is waited out (`finalizeWaitMs`, `driver/src/supervisor-plan.ts`) and adopted with its logged report, and a lost driver still alive steps into it until it learns its lease was lost, then hangs up on the group's tokens (`depart`), the wait outlasting that learning (one heartbeat) and the group's `takeoverBoundMs`. A finished one is adoptable until its Job's one-hour `ttlSecondsAfterFinished`. `driver/src/k8s/k8s-adopt.ts`, `driver/src/docker/docker-close-read.ts`.
- A taken-over run's agent (publish, review and its tool calls, `GET /tools` and `POST /tools/call`) and exporter reach the new holder through the supervisor's relay (`serveRelay`); a request in flight across the rebind is hung up on (the exporter retries it; the agent's proxy answers 502), and the transcript continues under the new claim from its first unacknowledged byte. `driver/test/supervisor.test.ts`, `driver/test/control-proxy.test.ts`.
- A taken-over run's agent gate requests reach the new holder the same way, and the agent holds no gate URL or token (`factory-gate` asks the control socket); an ad-hoc gate or exec run in flight across the rebind is hung up on and re-asked, so it may run on both holders, never exactly once. `driver/src/loop/loop-gates.ts`. A finish pass (`POST /gate/finish`) in flight across the rebind is hung up on and re-asked the same way and may run the gates on both holders; the helper re-asks under the request id it minted for that stop, which keys the round: a round already recorded is replayed (the red gate rerun for its output), never spent again, and the new holder reads both from the board. `driver/src/loop/loop-finish.ts`.
- A driver cut off from the board stops at its own lease clock, never at a failed beat: one lease after the last acknowledged beat's send time it departs (runner and group left for the next claim, never a verdict) or kills a runner not yet launched, and fences the conclusion's board calls; the review beat and the reclaim renew keep their own. `driver/src/loop/loop-lease.ts`, `driver/test/loop-lease-lapse.test.ts`.
- Stated limit: a rebind reaches a live supervisor only once the kubelet refreshes the attempt Secret's volume — up to its sync period (default one minute) plus its cache delay; docker's write is seen on the supervisor's next control poll. `driver/src/k8s/k8s-binding.ts`.
- Stated limit: a node going NotReady is seen only when the cluster acts on it (taint-based eviction, default ~300 s, then the Job's `FailureTarget`/`Failed` or the pod's deletion); the driver never treats stale pod status as loss. `driver/src/group-watch.ts`.
- Stated limit: a takeover needs `driver.rebindGraceMs` to outlast that refresh (~60 s measured); a shorter grace ends the group before the new holder's binding arrives. `charts/factory/values.yaml`, `scripts/test-k8s.sh`.
- Stated limit: why a driver ended a run is recorded on the attempt only where it outlives the kill — a hard-kill deletes the Job, its record, its Secrets and its claim before `end` reaches the board, a refused record is none — and such a run is redone in its tree and session. `driver/src/termination.ts`, `driver/src/k8s/k8s-runner.ts` (`killRunner`).
- Stated limit: a verdict neither staged nor completed within one lease leaves its group and checkout claim to the next claim: its agent outcome is adopted and resumes after the last post-run phase checkpointed on the board (`gates` bound to the tree's fingerprint, then `post`, `publish`); a phase whose checkpoint is missing, unreadable or bound to another tree runs again, with every phase after it, and an attempt with no budget left can retire `dead` before it is adopted. `driver/src/loop/loop-conclusion.ts` (`end`), `driver/src/loop/loop-phase-checkpoints.ts`.
- Stated limit: every runner class's node pools must span the zones task volumes live in, the default class's too since the reaper's export Job runs in it; a pod respecced into a pool that cannot reach its volume sits Pending until the claim is labelled `factory.task-unschedulable` (`driver/src/k8s/k8s-podspec.ts`, `volumeExportJobSpec`; `driver/src/k8s/k8s-group.ts`). A live group whose class is no longer declared is taken over, but its gate is not resized (`driver/src/k8s/k8s-gate.ts`); a finished run adopted, or a group respecced after a node loss, whose class is no longer declared is handed back as an interruption naming the class, within the interruption budget, its group and volume left — never failed, never moved to another class — and the next claim finishes it once the class is declared again (`runnerClassStep`, `driver/src/loop/loop-adopt.ts`; `jobClassOf`, `driver/src/runner-classes.ts`).
- Stated limit: a declared service image needs `sh`, `cat` and a writable `/tmp` — its liveness probe (`driver/src/scripts/service-generation-probe.sh`) fails on every run without them.
- Stated limit: a service `tmpfs` survives an in-pod sidecar restart (the pre-gate restart, a kubelet restart) and is empty only in a recreated pod, where docker's restart re-runs the container empty (`driver/src/services.ts`, `serviceRunArgs`); under a microVM RuntimeClass the guest does not enforce the emptyDir `sizeLimit`, so overflowing it is an OOM kill of the sidecar, bounded by its memory limit (`driver/src/k8s/k8s-podspec.ts`, `driver/src/k8s/k8s-podfields.ts`, `serviceResourcesField`).
- Stated limit: the kubernetes question round trip (a real claude CLI through the bridge) is not run on a kind cluster — the cluster lane installs the stub executor image. The relay is pinned offline in `driver/test/k8s/` and run through the supervisor with the stub's question (`--phase control`); docker's lane is `ask_roundtrip_lane` in `scripts/test-jobs.sh`. The same holds for the gated finish (claude's Stop hook, opencode's re-run): its relay and loop are pinned in `driver/test/k8s/gates-and-reviewer.test.ts` and `driver/test/loop/finish-pass.test.ts`, the real CLIs only by docker's `--phase finish-gate`.
- Deliberate docker divergences: a runner class carries resources only — one setting `runtimeClassName`, `nodeSelector`, `tolerations`, `affinity` or `docker` is refused at boot (`driver/src/runner-classes.ts`, `assertDockerClass`), and so is a set `RUNNER_SANDBOX_POOLS`: sandbox node pools are a kubernetes placement; no cpu-request flag, no `imagePullSecrets` twin, no admission equivalent; on docker (development only) service listeners are reachable by IP on the compose network (`driver/src/docker/docker-mailbox.ts`). Stated limit: a docker create the daemon refuses is typed only by its words (`startupCauseOf`); its CLI prints no status, so a refusal whose words prove no cause is left to the lease, where kubernetes fails a create the API server refuses with 422 as config (`specRefusalOf`).
- Stated limit: a docker class gives task code root over the task volume, so tool-uid isolation does not hold there — its `dockerd` runs privileged with the task volume mounted, and the socket's group 1000 holds the tool uid; the boundary is the class's microVM. The docker executor has no docker class (refused at boot, above). `driver/src/k8s/k8s-dockerd.ts`.
- Stated limit: admission trusts a docker class's RuntimeClass name, not its handler: a privileged `dockerd` is admitted in any pod whose `runtimeClassName` equals the class's, and so is a pod tolerating a sandbox pool's taint under any name the pool lists. So the driver refuses to start unless each docker class's RuntimeClass handler is `kata` or `kata-<variant>`, and the same for each class tolerating a pool's taint (`isolation.sandboxPools`, `RUNNER_SANDBOX_POOLS`; a keyless `Exists` toleration included, the effect not read), whose RuntimeClass must also be in that pool's list; gVisor (`runsc`) is refused, and a missing, forbidden or unreadable RuntimeClass refuses too. It reads the handler name, never what the node maps it to: a runc handler named `kata` gives task code the node. A RuntimeClass changed after boot is not re-read. The read is a ClusterRole `get` on `runtimeclasses`, scoped by `resourceNames` and rendered only with a docker class or a pool. `driver/src/k8s/k8s-runtime-class.ts`, `charts/factory/templates/driver-runtimeclass-rbac.yaml`, `charts/factory/templates/driver-admission.yaml`.
- Stated limit: the sandbox-pool policy is cluster-wide and identifies a pool by its taint alone (`charts/factory/templates/sandbox-admission.yaml`). Exempt namespaces (`isolation.sandboxExemptNamespaces`) run unfenced: the default `kube-system`, `gmp-system`, `gke-managed-*` holds the node DaemonSets a production GKE cluster runs unsandboxed with a tolerate-everything toleration; any other such DaemonSet is refused until its namespace is listed. A pod created before the policy that breaks it is refused on any later update, a finalizer removal included. Two releases' policies AND together, so two releases declaring different pools refuse each other's pods. `driver/test/k8s-sandbox-admission.test.ts`.
- Stated limit: CEL cannot read a Node, so with pools set every non-exempt pod created with `spec.nodeName` (or updated to set it) must name some pool's RuntimeClass, on any node; the scheduler binds through `pods/binding`, which the policy does not match, and DaemonSets place by affinity. `scripts/lanes/k8s/admission.sh`.
- Stated limit: GKE does not enforce the sandbox itself: on a MICROVM pool a pod with only the toleration was measured running under runc; for GKE Sandbox (gVisor) built-in enforcement is unconfirmed. The policy is the guard either way. `charts/factory/values.yaml`.
- Stated limit: a `dockerd` loss — its restart count moved, or it is not running at either read — is checked per verdict gate phase, not per gate: one seen after the phase fails is an infrastructure interruption, refunded under the node-loss bound — a loss under an earlier gate that passed included — but only twice in a row: the third consecutive dockerd loss on spends an attempt and the interruption budget. "Consecutive" is the board's interruption record, not the gate history: any other interruption between two dockerd losses starts the count again, an attempt that ended in a verdict does not. An unread daemon is a blocked interruption; the task pod is torn down, not kept, and the next claim redoes the attempt. An ad-hoc gate run gets a note only. A loss under a finish pass lets the agent stop and interrupts the attempt, never a verdict on the gates (`driver/src/loop/loop-finish.ts`). `driver/src/dockerd-loss.ts`.
- Stated limit: no lane starts a real `dockerd`; the kind cluster lane only admits and refuses its pod shape (`--phase admission`), so the sidecar runs only on a microVM node pool. `scripts/lanes/k8s/admission.sh`.
- Stated limit: a docker class's registry mirrors (`RUNNER_DOCKER_MIRRORS`) are kubernetes only, as docker classes are; they cover Docker Hub pulls alone (`ghcr.io`, `mirror.gcr.io` references pull directly), take only `https://` (an `http://` one needs `--insecure-registry`, refused at boot and render), and a private or in-cluster mirror needs its `/32` in `isolation.allowedCidrs`, which the pod-wide NetworkPolicy opens to the agent too. `driver/test/config.test.ts`, `scripts/test-k8s.sh`.
- Stated limit: a docker class runs only under a microVM (Kata) RuntimeClass, which needs nodes with nested virtualization (a machine shape that supports it, not a shared-core family) and adds the RuntimeClass's `overhead.podFixed` to every pod (about 250m/130Mi on the one measured pool). Every container is sized, since the VM is sized from the sum of its containers' limits: `resources` and `dockerResources` limits and a `dockerStorage` within the `dockerd` memory limit are required at boot and render. On every class the supervisor takes a fixed 500m/1Gi (a fetch needing more OOMs it), `task-init` and the exporter 250m/512Mi (`driver/src/k8s/k8s-podfields.ts`). The Docker data root is in memory, since a plain emptyDir is virtiofs in the guest and overlay2 cannot use it; the start script makes `/dev/kmsg`, which kind's nodes read. `driver/src/k8s/k8s-dockerd.ts`, `driver/src/scripts/dockerd-start.sh`, `driver/src/runner-classes.ts`.
- Stated limit: the chart default's cpu budget (limits summing to at most 11 under a microVM guest) covers the measured pod only — agent, supervisor, exporter, gate and two services; a reviewing pod adds a `reviewer` at the runner's CPU limit (+2 on chart defaults), and each further service adds 1 CPU. Memory is not budgeted: the measured pod's memory limits sum to about 35.5 GiB, and the gate's in-memory `/tmp` counts against the gate's own memory limit, so a suite whose scratch outgrows it is OOM-killed rather than spilled to disk. `charts/factory/values.yaml`, `driver/test/k8s/pod-spec.test.ts`.
- A node loss never spends the poison interruption budget: the driver flags `nodeLoss` only on structured evidence — a drain, a runner pod the control plane marked a disruption target, evicted, ended for its node's shutdown or gone (`runnerLossOf`), a supervisor's finalized exit-143 SIGTERM kill that no driver kill record explains (the platform terminating the pod, `platformTerminated`), a pod seen then gone before its supervisor's first contact, and a lost supervisor channel only when the pod list confirms the group was taken away (`groupTakenAway` answers `taken`, `kept` or `unknown`: a live pod whose supervisor crashed or was OOM-killed is `kept` and keeps counting; a failed, timed-out, empty or malformed read is `unknown`, a blocked interrupt that spends no budget — stated limit: a persistently faulty apiserver under a supervisor that keeps closing re-queues the task with no bound); the docker counterpart is a removed container; lease expiry stays unflagged
- Stated limit: a suspended organization's task volumes are kept for the whole suspension, so a thread's `taskVolume.size` claim is billed until the organization is reactivated or deleted; the suspension stops its runner pods, never its volumes.
- The secret store's `gcp` backend authenticates through the dashboard service account's `iam.gke.io/gcp-service-account` annotation, so no pod holds a credential; `eks.amazonaws.com/skip-containers: wait-for-database` is always set (limit: EKS Pod Identity has no per-container exclusion, so its credentials reach the init container too).

## EKS prerequisites

Each is silent when wrong. Walk: [eks-runbook.md](eks-runbook.md); measured claims: [limits.md](limits.md).

- **Node-level IMDS defence** — `httpPutResponseHopLimit: 1` on the runner node group.
- **The VPC CNI add-on needs `enableNetworkPolicy: true`**, enforcing only on EC2 Linux nodes — not Fargate, not Windows. Without it the NetworkPolicy is admitted and inert.
- **Every runner pod is a Job's** — the driver creates no bare pod — closing AWS's standalone-pod caveat (`charts/factory/templates/driver-rbac.yaml`).
- **metrics-server is not installed by default** (vitals read null), and **`blockedCidrs` blocks the VPC too** — a runner that must reach a VPC endpoint needs that host in `isolation.allowedCidrs` as a /32.
- **The task volume** needs the EBS CSI driver add-on running and a StorageClass with `provisioner: ebs.csi.aws.com`, `volumeBindingMode: WaitForFirstConsumer`, `type: gp3`, `reclaimPolicy: Delete`, named by `taskVolume.storageClass` (the default `''` fits kind, nothing on EKS); the operator creates it ([eks-runbook.md](eks-runbook.md)). **Only the driver's task pods set `fsGroup`** (`core/test/docs.eks-storage.test.ts`), which makes the block volume writable by uid 1000. Stated limit: `ReadWriteOncePod` on the EBS CSI driver and the chart on EKS have never been observed.

## Isolation: assumptions and residuals

Controls and why none of this is kernel or VM isolation: [security.md](security.md). The deployment must provide
**A CNI that enforces NetworkPolicy**, **ValidatingAdmissionPolicy, native sidecars and `pods/resize`, Kubernetes ≥ 1.33**,
the IMDS defence. Residuals:

- **IPv6 egress is not covered**; every rule is IPv4.
- A runner can **reach the driver pod on any port** (the gate endpoint has an ephemeral port). Runner pods take no ingress, so one attempt cannot reach another (`--netpol` pins it denied); a declared service name resolves to `127.0.0.1` through `hostAliases`, never through DNS (#296).
- An apiserver or node address that is **PUBLIC is not covered** by `blockedCidrs`. A NetworkPolicy also **says nothing about HTTP routes**.
- A thread's disk is its `taskVolume.size` request, a cap only where the provisioner enforces it; `REVIEWER_UID` separates signals, not files.
