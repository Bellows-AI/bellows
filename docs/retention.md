# Retention

How long an organization's task history is kept: its plan's window, after which one pass deletes every thread that settled before it, with its objects and rows.

## Invariants

- **The clock is the thread's last settle**: a thread is eligible only when every member and review is terminal (`server/src/db/task-summary.ts:10`), no `workflow_wait` of its root is pending, and its newest `finished_at` is older than the effective days. A suspended org's interrupted runs are queued again, never terminal; the pass skips every org that is not `active`.
- **Only a task root is a candidate.** Follow-ups, retries and workflow successors share their root's `root_job_id`; a named-profile review is its own root but is stamped and deleted only with the thread whose member it reviews, and its runs count in that thread's clock. A batch task's root goes only with its batch.
- **Windows**: Free is the cloud default, 7 days; Pro 180 and Enterprise's days arrive by push. The board names no plan. Self-hosted with no `PLAN_DEFAULT_MAX_RETENTION_DAYS` is unlimited: no thread expires, and `ARTIFACTS_RETENTION_DAYS` (`server/src/config-artifacts.ts`) keeps timing deleted skills.
- **One knob per deployment**: cloud refuses `ARTIFACTS_RETENTION_DAYS`, and any board refuses it beside `PLAN_DEFAULT_MAX_RETENTION_DAYS`; the chart renders it empty by default, which reads as unset.
- **An upgrade applies at once, a downgrade after a 30-day notice** (`DOWNGRADE_NOTICE_DAYS`, decided): a lower target sets pending days and writes one `system` audit row `org.retention_downgrade`; a target at or above the effective days clears it. No `org_retention` row is unlimited, so every org's first window, at rollout or later, is a downgrade with notice (decided). A plan push and a deletion start take one per-org transaction lock (`planChangeLockKey`): an upgrade that commits first lifts every stamp it covers; one that commits after a deletion started does not stop it.
- **Bounds**: a pass every hour, at most 120 s like `ORG_PURGE_PASS_MS`; orgs least recently served first, each leased to one pass (`claim_owner` token, `claimed_until`); a release clears only its own lease; per org per pass at most 100 threads stamped and 100 units expired, object pages of `LIST_LIMIT` (`server/src/artifacts/object-store.ts:28`), ten 10 000-row deletes of points and one of branch rows, object deletes in fenced chunks of 100. Each step is its own short transaction, one at a time, so a cross-org pool of one connection completes; every step is safe to run again, so a cut pass resumes.
- **No index on a large table**: candidates walk `job_org_root` and need a root created before the cutoff. A point carries the org its session's owner row, task binding or branch row resolved (`metric_point_org_of`), so the pass walks those three per org and deletes old points through `metric_point_session`; an old branch row stays only while it is the last link to a session with points. A point with no `org_id` belongs to no org's window, is read by no org, and stays (a stated limit).
- **Order: fence, drain, deletion start, secrets, objects, rows.** Under the thread's root row and lock, eligibility re-checked there, the root and its reviews are stamped (`thread_expiry`); `lockThreadRootInTx` then finds the thread gone, re-reading the stamp after its lock so a racing follow-up sees it. Every artifact write reads the stamp beside the org fence right before its put under `OBJECT_WRITE_BOUND_MS`; the pass lists the prefixes only `OBJECT_WRITE_DRAIN_MS` after the stamp. Before the first destructive step, `deleting_at` is written under the plan-change lock with the window re-checked; from then the unit is only finished, never revived. The rows go in one transaction; the stamp outlives them by a day.
- **An unconfirmed list, delete or collect retries**: the thread stays stamped for the next pass with a closed error code (`thread_expiry.last_error`), never reported gone ([organizations.md](organizations.md)'s purge rule). A board lost mid-step leaves the stamp, so no claim or follow-up revives a half-deleted thread.
- **One door to destruction**: every statement that deletes, inserts or updates a row (but the lease row) runs in `fencedStep`, which takes the plan-change lock and the lease row, stops the pass unless it still owns an unexpired lease (and extends it), and re-derives the window from the current plan in that transaction; the cutoff it hands over is SQL. A window read earlier only selects candidates. `server/test/org-retention.fence-structure.test.ts` fails a destructive statement outside it.
- **The pass reads absence, so it runs on the cross-org pool** and joins the list in [row-level-security.md](row-level-security.md); under the request role it refuses to run.
- **Logs carry counts only**: one `retention.pass` line per org per pass (org id, window, counts, closed error codes); never a thread id, repo, title, command or object key.

## Stated limits

- Database backups and the server's log pipeline keep deleted data until their own expiry, set by the cloud infrastructure outside this repo.
- Which plan carries which window (pricing copy) and the processor review live outside this repo.
- A volume is reaped only by a running driver stamped with this board's identity ([workspace.md](workspace.md)).
- An artifact index row a writer inserts after the row step, whose put the fence then refuses, stays: ids and a digest, no content.
- A telemetry point with no `org_id` (its session was never resolved to an org) is under no window and stays.
